Operating principles

Every phase is built against these. They come straight from the ADRs and AGENTS.md — a change to any of them is an architecture decision, not an implementation detail.

  • Shell first, behaviour later. Build all screens against mock data, then replace the mock with real services phase by phase. The screen code talks to real service signatures from day one.
  • Deterministic core, no AI in the critical path. Priority, planning, readiness, revision and pressure are pure functions of versioned config + evidence. Same inputs → same output, always.
  • Dates drive everything. Phases and scheduling derive from PreparationPlan / PlanPhase dates. No branching on calendar month — ever.
  • Config is versioned data. Weights, recency factors, urgency multipliers and intervals live in records like readiness-v1; every snapshot stores the version that produced it.
  • Evidence is immutable. Sessions, assessments, errors and readiness snapshots are never overwritten. Recalculation produces new rows; corrections are auditable.
  • Official ≠ derived. Board-official weightage and app-derived importance are different columns with different source_types, and never rendered as each other.
  • Never silently exceed capacity. When the plan can’t fit, it surfaces trade-offs; it does not quietly overbook the student.
  • Every task ships its tests. Unit tests for domain rules, integration for persistence, and the regression fixture for anything touching the engines — in the same change.

Cross-cutting workstreams

These aren’t phases — they run through every phase and are part of each task’s definition of done.

  • Config versioning — no magic constants in UI or API code; snapshots record the version used.
  • Domain events — persisted from Phase 0, emitted as each engine comes online, delivered only in Phase 7.
  • Auth & RBAC — server-side role checks; single family in the MVP but tenant boundaries in the schema; parent-safe endpoints separate by construction.
  • Determinism harness — scheduler / readiness tests freeze current date, timezone, config version and fixture.
  • Regression suite — the 18 scenarios in TEST_STRATEGY.md are the acceptance gate; a task isn’t done until its scenarios and the relevant existing ones pass.
  • Migrations discipline — reversible migrations; FKs and uniqueness constraints wherever a domain invariant allows.
  • Provenance integrity — OFFICIAL and DERIVED_* never conflated, in data or UI; synthetic data stays labelled.

Risks & open decisions

  • Real curriculum data. Everything today is synthetic. Before production, a real CBSE curriculum + official unit weightage import pass is needed, with full provenance. This is its own mini-project inside Phase 0 / later.
  • iOS reminder reliability. Web push on iOS is weak. Tier 1 calendar export is the dependable path — set that expectation rather than promising alarm-grade push.
  • Projected-score trust. Keep the model conservative and versioned; the bigger risk is users over-trusting a planning estimate as a predicted result.
  • UI-shell rework. View-model seams limit churn, but expect real refactors when the planner (Phase 2) and projection (Phase 4) replace their mocks.
  • Auth provider. Phase 6 forces the choice; pick it earlier if the team has a preference, so the seam is in place.

  • Curriculum & versioning with provenance

  • Spaced revision, date-driven
  • Assessment & error feedback loop

  • Weekly review
  • Plan-risk detection before the deadline
  • Date-derived revision & exam behaviour
  • Automated validation across all of it
